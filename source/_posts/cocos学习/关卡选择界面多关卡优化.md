## 0. 为什么这题会难

一个"N 个关卡的选择界面"，N=20 随手写都能跑。但是：

- N=500，每个关卡要下载一份 JSON？—— 首屏等 30 秒
- 每个关卡要渲染一张图？—— Draw Call 和 GPU 节点爆炸
- 用户滚动浏览再回来，再次下载？—— 流量爆炸
- 加载失败反复重试？—— 后台埋点雪崩

**问题不是"写不出来"，是"写出来的东西不能上生产"。**

下面这张表是一个典型多关卡界面**至少**要考虑的 7 个瓶颈：

| # | 瓶颈 | 症状 | 主要方案 |
|---|------|------|---------|
| 1 | **渲染** | FPS 崩、滑动卡帧 | 虚拟列表 / 节点复用、动态图集、Label Cache |
| 2 | **内存** | 常驻 >500MB、OOM | 保留窗回收、大数据单独管、释放 Texture |
| 3 | **网络** | 首屏 5MB 下不完 | 按需下载、分页、并发去重 |
| 4 | **冷启动** | 每次开游戏都重下 | 本地缓存（localStorage / file）、首屏预热 |
| 5 | **CPU 高频事件** | 滚动时主线程忙 | 节流、冗余索引、避免空转 |
| 6 | **事件分发** | 一次点击触发多处逻辑 | 事件冒泡控制、事件源判断 |
| 7 | **生产稳定性** | 线上偶发崩、埋点雪崩 | 失败自愈、上报去重、fallback |

你可能只想到"虚拟列表 + 按需下载 + 本地缓存"这三招 —— **那只覆盖第 1、3、4 三个瓶颈**。剩下的 4 个会在上量后把你按在地上摩擦。

## 1. 先认识几个关键 API（新手必读）

下面这些是全文示例里频繁出现的 Cocos 3.x API，**先眼熟**。记不住没关系，**知道"有这个东西"就行**，用的时候回头查。

### 1.1 渲染相关

```typescript
import { _decorator, Component, Node, Prefab, instantiate, ScrollView,
         UITransform, Sprite, SpriteFrame, Texture2D, ImageAsset,
         Label, assetManager, resources, sys } from 'cc';
```

- `ScrollView` — 滚动容器组件，提供 `scrolling / scroll-ended` 事件
- `instantiate(prefab)` — 从 Prefab 克隆一个节点
- `Texture2D / ImageAsset` — 贴图对象，可以从字节流手动构造
- `Sprite + SpriteFrame` — 精灵渲染
- `Label` — 文本（**注意 Label 频繁变内容也卡，每次改 string 都会重建 cache**）

### 1.2 资源与网络相关

| API | 干什么 |
|---|---|
| `resources.load(path, type, callback)` | 从 `resources/` 加载资源（editor 内建） |
| `assetManager.loadRemote(url, callback)` | 加载远端资源（图片 / JSON） |
| `assetManager.loadBundle(name, cb)` | 加载 Bundle（分包） |
| `sys.localStorage.setItem / getItem` | 跨平台本地 KV（原生、H5、小游戏都兼容） |
| `new Texture2D()` + `tex.reset({width,height,format})` + `tex.uploadData(buf)` | 从字节流构造贴图 |

**新手记住一件事**：`resources.load` 只能读工程内的 `resources/` 目录；线上动态下发的 JSON 用 `assetManager.loadRemote`。别搞混。

### 1.3 事件相关

| 事件 | 来源 | 常用 |
|---|---|---|
| `'scrolling'` | `ScrollView` | 滚动时持续触发，拿 `scrollOffset` |
| `'scroll-ended'` | `ScrollView` | 滚动停止时触发一次 |
| `'click'` / `Node.EventType.TOUCH_END` | `Button` / `Node` | 点击 |
| `Node.EventType.TOUCH_START` | `Node` | 按下 |

**触发模式核心区别**：

| 触发方式 | 说明 | 适用 |
|---|---|---|
| `node.on('event', cb, this)` | 绑定在**这个节点**上 | 需要明确事件源时 |
| `node.on('event', cb, this, true)` | useCapture=true 捕获阶段 | 父节点提前拦截 |
| `eventTarget.emit('name', data)` | 自定义事件总线 | 跨模块通信 |

**什么时候用 `EventTarget` 总线**：**跨模块通信**，列表界面想知道"玩家打通关了"—— 总线 emit 一下，列表界面 on 一下，双方不互相 import。**几乎所有列表刷新信号都应该走总线**，这是坑里摔出来的经验。

## 2. 渲染瓶颈

### 2.1 虚拟列表 — 只渲染可见区

#### 问题

N=1000 个节点同屏 = GPU + 合批直接死。Cocos 3.x 的渲染代价**和可见节点数正相关**，不是"看不见就不渲染"（`active=false` 的节点确实会跳过，但只是省了渲染，节点本身依然占内存）。

#### 方案

**核心思想**：只实例化可见区的 N 个 item 节点（一般 20~30 个），滚动时复用这些节点，只改它们的 `position` 和数据。

Cocos 3.x 官方提供了 `ScrollView`，但它**不自带虚拟化**，虚拟化要自己写。思路就这几行：

```typescript
// 可见区数学：给定滚动偏移 + 视口高 + item 高，算出哪几行要显示
function computeVisibleRange(
    scrollOffset: number,   // content 偏移量（ScrollView 给你）
    viewportSize: number,   // 视口高度
    itemSize: number,       // 每行固定高
    totalCount: number,     // 总行数
    buffer: number = 2,     // 可见区外多渲染几行，避免滚动边缘白边
): [number, number] {
    const first = Math.max(0, Math.floor(scrollOffset / itemSize) - buffer);
    const last  = Math.min(totalCount - 1,
                           Math.ceil((scrollOffset + viewportSize) / itemSize) + buffer);
    return [first, last];
}
```

#### 最小示例（虚拟列表组件）

```typescript
import { _decorator, Component, Node, Prefab, instantiate, ScrollView,
         UITransform, Vec3 } from 'cc';
const { ccclass, property } = _decorator;

@ccclass('VirtualList')
export class VirtualList extends Component {
    @property(ScrollView) scrollView: ScrollView = null!;
    @property(Node)       content:    Node       = null!;     // ScrollView.content
    @property(Prefab)     itemPrefab: Prefab     = null!;
    @property             itemHeight: number     = 120;
    @property             cols:       number     = 2;          // 每行几列
    @property             gap:        number     = 10;
    @property             buffer:     number     = 2;

    private data: LevelData[] = [];
    private pool: Node[]      = [];      // 节点池（复用）
    private busy: Map<number, Node> = new Map();  // 当前占用：rowIndex -> node

    setData(data: LevelData[]) {
        this.data = data;
        const rowCount = Math.ceil(data.length / this.cols);
        const rowH = this.itemHeight + this.gap;

        // 1. content 总高 = 行数 × 行高
        const ut = this.content.getComponent(UITransform)!;
        ut.setContentSize(ut.width, rowCount * rowH);

        // 2. 监听滚动
        this.scrollView.node.on('scrolling', this.onScroll, this);

        // 3. 手动刷新一次
        this.onScroll();
    }

    private onScroll() {
        const viewport = this.scrollView.view!.getComponent(UITransform)!.height;
        const offset   = this.scrollView.getScrollOffset().y;  // 顶部偏移
        const rowH     = this.itemHeight + this.gap;
        const totalRows = Math.ceil(this.data.length / this.cols);

        const [first, last] = computeVisibleRange(offset, viewport, rowH, totalRows, this.buffer);

        // 回收不在可见区的行
        for (const [row, node] of this.busy) {
            if (row < first || row > last) {
                node.active = false;
                this.pool.push(node);
                this.busy.delete(row);
            }
        }

        // 为可见区的行分配节点
        for (let row = first; row <= last; row++) {
            if (this.busy.has(row)) continue;
            const node = this.pool.pop() ?? instantiate(this.itemPrefab);
            node.setParent(this.content);
            node.active = true;
            node.setPosition(new Vec3(0, -row * rowH, 0));
            this.renderRow(node, row);
            this.busy.set(row, node);
        }
    }

    private renderRow(rowNode: Node, rowIndex: number) {
        // rowNode 下挂 cols 个 item 子节点
        // 按 rowIndex*cols + c 取数据，给每个子节点填 name / icon / state
        // ...
    }

    onDestroy() {
        this.scrollView?.node.off('scrolling', this.onScroll, this);
    }
}

interface LevelData {
    tableId: number;
    name: string;
    iconUrl: string;
    state: 0 | 1 | 2;   // 未加载 / 加载中 / 已加载
}
```

#### 关键要点（坑指南）

1. **总行数不是总 item 数**：2 列 N 个 item，行数 = `ceil(N/2)`
2. **`buffer` 表示"可见区上下多画几行"**，给滚动衔接缓冲，一般 1~2
3. **节点池不要无限扩**：可见区最多 `(rows+1)*cols` 个，超了就说明 buffer 开太大
4. **`content` 的 `setContentSize` 一定要设**，不然 ScrollView 不知道能滚多远
5. **滚动事件是高频的**（见 6.1），如果里面算得复杂，记得节流

### 2.2 动态图集 / Texture2D 字节流 — 让 N 个 icon 合批

#### 问题

1000 个关卡 icon，每个 icon 一张独立 png = 1000 个 SpriteFrame = 1000 个贴图 = Draw Call 灾难。即使用同一个 Sprite 材质，**不同贴图之间断合批**，真机一个节点一个 DC。

#### 方案 A：动态图集（官方推荐，合并同材质 Sprite）

Cocos 3.x 编辑器里可以配置**动态图集**，自动把小图合并到一张大图：

```
项目设置 → 项目数据 → 动态图集 → 启用动态图集
```

前提：Sprite 材质必须一致，贴图尺寸不超过配置的单图最大边长（默认 512）。

#### 方案 B：Texture2D 直接画字节流（适合像素图 / 程序生成）

如果 icon 是像素画或者能用"调色板 + RLE"表达，服务端下发字节流，客户端手动构造贴图：

```typescript
import { Texture2D, ImageAsset, SpriteFrame, gfx } from 'cc';

/** 从 RGBA8888 字节流构造一张 SpriteFrame */
function createSpriteFrameFromBytes(
    pixels: Uint8Array,     // length = width*height*4
    width: number,
    height: number,
): SpriteFrame {
    // 1. ImageAsset 承载原始 buffer
    const image = new ImageAsset({
        _data: pixels,
        _compressed: false,
        width,
        height,
        format: Texture2D.PixelFormat.RGBA8888,
    });

    // 2. Texture2D 包装 ImageAsset
    const tex = new Texture2D();
    tex.image = image;
    tex.setFilters(Texture2D.Filter.NEAREST, Texture2D.Filter.NEAREST);   // 像素图必须 NEAREST 避免糊
    tex.setWrapMode(Texture2D.WrapMode.CLAMP_TO_EDGE, Texture2D.WrapMode.CLAMP_TO_EDGE);

    // 3. SpriteFrame 包装 Texture2D
    const sf = new SpriteFrame();
    sf.texture = tex;
    return sf;
}
```

#### RLE 解码（服务端下发调色板 + 索引串）

```json
{
  "gridSize": 50,
  "palette": ["#FFFFFF", "#000000", "#FFD700"],
  "pixels": "0:100,1:50,2:10,0:2340"
}
```

- `gridSize`：边长
- `palette`：hex 颜色表
- `pixels`：RLE 压缩，`"调色板索引:重复次数"`

```typescript
function decodePixels(gridSize: number, palette: string[], rle: string): Uint8Array {
    const total = gridSize * gridSize;
    const buf = new Uint8Array(total * 4);

    // 预解析 palette（hex → rgb）
    const rgb = palette.map(hex => {
        const h = hex.startsWith('#') ? hex.slice(1) : hex;
        return {
            r: parseInt(h.slice(0, 2), 16),
            g: parseInt(h.slice(2, 4), 16),
            b: parseInt(h.slice(4, 6), 16),
        };
    });

    let p = 0;
    for (const seg of rle.split(',')) {
        const colon = seg.indexOf(':');
        if (colon < 0) continue;
        const pi = parseInt(seg.slice(0, colon), 10);
        const cnt = parseInt(seg.slice(colon + 1), 10);
        const c = pi >= 0 ? rgb[pi] : null;
        for (let i = 0; i < cnt && p < total; i++, p++) {
            const o = p * 4;
            if (c) {
                buf[o] = c.r; buf[o + 1] = c.g; buf[o + 2] = c.b; buf[o + 3] = 255;
            } else {
                buf[o + 3] = 0;   // 透明
            }
        }
    }
    for (; p < total; p++) buf[p * 4 + 3] = 0;
    return buf;
}
```

#### 为什么值

- JSON 比 png 小 10~50 倍（RLE + 调色板索引只有 1 字节）
- 不用 HTTP 拉图片 + 图片解码管线
- 像素数据还能和画刷叠加（玩家涂色实时改贴图）

### 2.3 精修刷新 — 只刷那一格

#### 问题

进二级页面（比如进关卡玩了一把）回到列表，**只有一个 item 的状态变了**。简单做法是整个列表 `setData` 重刷 = 全部 item 重新实例化渲染 = 卡。

#### 方案

维护一个字段 `lastPlayedIndex: number`（默认 -1）：

- 点击 item 进关卡前写入当前索引
- 从关卡回到列表时，读出这个索引
- 只刷这一行对应的节点，不动其他节点

```typescript
onReturnFromLevel() {
    const idx = this.lastPlayedIndex;
    this.lastPlayedIndex = -1;   // 立刻 reset，避免重复触发
    if (idx < 0) return;

    // 更新这一条数据（state、星级、进度条）
    this.data[idx].state = 2;
    this.data[idx].stars = GameSave.getStars(this.data[idx].tableId);

    // 只刷这一行对应的节点，不触发整个 ScrollView 重建
    const rowIndex = Math.floor(idx / this.cols);
    const node = this.busy.get(rowIndex);
    if (node) this.renderRow(node, rowIndex);
}
```

视觉上只有这一格变，代价 O(1)。

**数据结构就是一个 number，带来的是首页永远丝滑。"好的优化不是增加代码，是增加一个数字让别人少写代码"**。

## 3. 内存瓶颈

### 3.1 SpriteFrame / Texture2D 必须手动释放

#### 问题

Cocos 3.x 的 `assetManager.loadRemote` 加载的贴图**不会自动释放**（默认 refCount 引擎不管）。滚到底内存 500MB 涨不回来 = OOM 是常态。

#### 方案

两种释放方式，选一个用顺手：

```typescript
// 方式 A：显式减引用（推荐，可控）
assetManager.loadRemote<ImageAsset>(url, (err, img) => {
    if (err) return;
    this.cache[idx] = img;
    img.addRef();            // 自己管引用
});

// 回收时
const img = this.cache[idx];
img.decRef();                // 引用归零时引擎自动释放
this.cache[idx] = null;

// 方式 B：Texture2D.destroy()
const tex = this.textures[idx];
tex.destroy();               // 立刻释放 GPU 资源
this.textures[idx] = null;
```

**别偷懒用 `assetManager.releaseAsset`**：在一些版本里释放顺序有坑，容易把正在显示的纹理一起干掉，屏幕花屏。**显式 `addRef/decRef` 最稳**。

### 3.2 保留窗回收 — 大数据主动释放

#### 问题

不回收 = 滚到底内存爆炸。1 个 icon 512×512 RGBA = 1MB，1000 关 = 1GB。

#### 方案

- **保留窗 = 可见区 ± 一屏（keepBuffer）**
- 窗外的已加载项：释放 Texture / SpriteFrame，state 归 0
- 重滚回来时三态机会自然重新下载

```typescript
private recycleOutOfWindow() {
    const viewport = this.scrollView.view!.getComponent(UITransform)!.height;
    const offset   = this.scrollView.getScrollOffset().y;
    const rowH     = this.itemHeight + this.gap;
    const totalRows = Math.ceil(this.data.length / this.cols);

    const [first, last] = computeVisibleRange(offset, viewport, rowH, totalRows, this.buffer);
    const firstIdx = first * this.cols;
    const lastIdx  = Math.min((last + 1) * this.cols, this.data.length);

    // 保留窗 = 可见区 + 上下各一屏
    const keep = (last - first + 1) * this.cols;
    const keepFirst = Math.max(0, firstIdx - keep);
    const keepLast  = Math.min(lastIdx + keep, this.data.length);

    let recycled = 0;
    // ⭐ 遍历 loadedSet 而不是 0..N —— O(loaded) 代替 O(N)
    for (const i of this.loadedSet) {
        if (i < keepFirst || i >= keepLast) {
            this.iconCache[i]?.decRef();    // 或者 .destroy()
            this.iconCache[i] = null;
            this.data[i].state = 0;
            this.loadedSet.delete(i);       // Set 迭代中 delete 合法
            recycled++;
        }
    }
    return recycled;
}
```

#### 关键要点

1. **`keep` 必须 ≥ 可见区大小**，否则"可见但刚好在窗边的 item"会被错误回收、滑动变灰
2. **`state=1`（加载中）不回收** —— 请求在路上，回收了回调找不到 entry
3. **迭代 Set 时 delete 是合法的**（V8 / JSC 规范保证）
4. **为什么 `loadedSet` 那么重要**：1000 条列表、当前 loaded 30 项，回收扫 30 次 vs 1000 次。这叫**"访问模式决定数据结构"**

### 3.3 小数据放 Component 字段，大数据放单例 Map

#### 问题

每个列表组件 `@property` 字段太多会让 Prefab 膨胀、序列化变慢，且**大 buffer 不适合挂在节点组件上**（跨场景切换会挂一堆）。

#### 方案

小状态（数字、字符串数组）放组件字段；大缓存（Uint8Array、Texture2D、SpriteFrame 池）放**单例 Manager**：

```typescript
export class LevelIconCache {
    private static _inst: LevelIconCache;
    static get inst() { return this._inst ??= new LevelIconCache(); }

    private pixels:  Map<number, Uint8Array>  = new Map();   // 原始像素
    private frames:  Map<number, SpriteFrame> = new Map();   // 贴图
    readonly loaded: Set<number>              = new Set();
    readonly pending:Set<number>              = new Set();

    set(tableId: number, pixels: Uint8Array, frame: SpriteFrame) {
        this.pixels.set(tableId, pixels);
        this.frames.set(tableId, frame);
        this.loaded.add(tableId);
    }
    getFrame(tableId: number) { return this.frames.get(tableId); }
    drop(tableId: number) {
        this.frames.get(tableId)?.destroy();
        this.frames.delete(tableId);
        this.pixels.delete(tableId);
        this.loaded.delete(tableId);
    }
    // 场景切换或整屏销毁时
    clear() { for (const id of this.loaded) this.drop(id); }
}
```

#### 心法

**数据的"住所" = 访问频率 × 大小 × 生命周期**：

- 每帧读、频繁变、体积小 → 组件字段
- 体积大、多场景共享、生命周期 > 单个节点 → 单例 Map
- 临时中间态 → 局部变量

## 4. 网络瓶颈

### 4.1 按需下载 — 滚到哪下到哪

#### 三态机

`data[i].state`：

- `0` = 未加载（灰 / 占位）
- `1` = 加载中（灰 + 菊花）
- `2` = 已加载（真图）

**为什么不是两态**：没有 0 就没法区分"从未下过"和"回收过的"，回收机制无法表达。

#### 状态转换

```
              markVisible         下载成功
0（未加载） ─────────────> 1（加载中） ──────────> 2（已加载）
 ▲                         │                        │
 │                         └──── 下载失败 ──────────┘
 │                                                  │
 └──────────── recycle（回收） ────────────────────┘
```

**任何状态都能回到 0**（合法起点）= 失败自愈。

#### 可见区扫描

```typescript
private markVisibleItems(): number[] {
    const [first, last] = this.currentVisibleRowRange();
    const firstIdx = first * this.cols;
    const lastIdx  = Math.min((last + 1) * this.cols, this.data.length);

    const newly: number[] = [];
    for (let i = firstIdx; i < lastIdx; i++) {
        if (this.data[i].state === 0) {
            this.data[i].state = 1;
            LevelIconCache.inst.pending.add(i);
            newly.push(i);
        }
    }
    return newly;
}
```

### 4.2 pendingMap — 按 url 查表支持并发去重

#### 问题

`assetManager.loadRemote` 回调只带 url 和资源，不带"我是第几次请求"：

- **回调顺序不保证**
- **同一 url 可能并发**（滚出屏幕又滚回来，state 从 2→0→1 再发一次）

#### 方案

```typescript
type PendingEntry = { tableId: number; idx: number; startTime: number };
private pendingMap: Map<string, PendingEntry[]> = new Map();
```

- key = url（回调用 url 查）
- value = **数组**（同 url 并发时 push 多条，`shift()` 按发起顺序取）
- entry 存 `tableId + idx + startTime`

#### 如果 value 是单值会怎样

第二次请求覆盖第一次的 entry，第一次回调到时找不到 entry，UI 卡在 state=1 永远翻不到 2。

#### 示例

```typescript
// 发请求
private startBatchLoad() {
    const now = Date.now();
    for (const i of LevelIconCache.inst.pending) {
        if (this.data[i].state !== 1) continue;
        const tableId = this.data[i].tableId;
        const url = `https://cdn.example.com/levels/${tableId}.json`;

        let queue = this.pendingMap.get(url);
        if (!queue) { queue = []; this.pendingMap.set(url, queue); }
        queue.push({ tableId, idx: i, startTime: now });

        assetManager.loadRemote<JsonAsset>(url, (err, json) => {
            this.onJsonLoaded(url, err, json);
        });
    }
}

// 处理回调
private onJsonLoaded(url: string, err: Error | null, json: any) {
    const queue = this.pendingMap.get(url);
    if (!queue || queue.length === 0) return;
    const entry = queue.shift()!;             // ⭐ FIFO 取出
    if (queue.length === 0) this.pendingMap.delete(url);

    // 快路径 + fallback：处理分页追加导致的索引错位
    let idx = entry.idx;
    if (this.data[idx]?.tableId !== entry.tableId) {
        idx = this.data.findIndex(d => d.tableId === entry.tableId);
        if (idx < 0) return;   // 条目已被移除
    }

    LevelIconCache.inst.pending.delete(idx);

    if (err || !json) {
        this.data[idx].state = 0;   // 退回 0，重滚回来自然重试
        this.traceDownloadFail(entry.tableId, err?.message);
        return;
    }

    // 解码像素 + 构造 SpriteFrame
    const raw = json.json as { gridSize: number; palette: string[]; pixels: string };
    const pixels = decodePixels(raw.gridSize, raw.palette, raw.pixels);
    const frame  = createSpriteFrameFromBytes(pixels, raw.gridSize, raw.gridSize);
    LevelIconCache.inst.set(entry.tableId, pixels, frame);
    this.data[idx].state = 2;

    // 顺手落盘（见 5.1）
    sys.localStorage.setItem(`level_icon_${entry.tableId}`, JSON.stringify(raw));

    // 只刷这一行
    const rowIndex = Math.floor(idx / this.cols);
    const node = this.busy.get(rowIndex);
    if (node) this.renderRow(node, rowIndex);
}
```

### 4.3 分页加载 — 首页先下 300KB

#### 问题

N=2000 一个大 JSON 5MB，首屏启动下 5MB 体验崩盘。

#### 方案

服务端切成 `page_1.json`（首页 30 条）+ `page_2.json / page_3.json / ...`，客户端：

- Boot 先同步合并首页
- 后台串行拉分页 2/3/4
- 每页合并后**整体赋值 `this.data`**，再重算 `content` 高度

#### 追加时的陷阱

```typescript
// ❌ 只 push，ScrollView 不知道总高变了
this.data.push(...newItems);

// ✅ 正确：append 后重算 content 高度
this.data.push(...newItems);
const rowCount = Math.ceil(this.data.length / this.cols);
const rowH = this.itemHeight + this.gap;
this.content.getComponent(UITransform)!.setContentSize(
    this.content.getComponent(UITransform)!.width,
    rowCount * rowH,
);
this.onScroll();   // 重算可见区
```

#### 探页到 404 — 分页终点的简约信号

客户端不知道总共几页？**不用在 config 里写总页数，也不用 server push**：从 `_1.json` 开始探，返回 404 就是终点。

- 服务端只管扔文件
- 客户端只管连请求直到 404
- 看到一串 404 日志别慌 —— 这是**正常终止信号**

```typescript
private async loadAllPages() {
    for (let p = 1; ; p++) {
        const url = `https://cdn.example.com/levels/page_${p}.json`;
        const ok = await this.loadOnePage(url);
        if (!ok) break;   // 404 / 网络错，视为终点
    }
}
```

## 5. 冷启动瓶颈

### 5.1 sys.localStorage — 跨平台 KV

#### 问题

每次开游戏都重下。老用户"昨天看过的 1000 张图"今天全要重走网络，白嫖不到"已经下过"的事实。

#### 方案

Cocos 3.x 的 `sys.localStorage` 是跨平台 KV 封装：

- 原生 → 本地文件系统
- H5 → 浏览器 localStorage
- 微信小游戏 → `wx.setStorage`

**你只管调 `setItem` / `getItem`**，底层差异被隐藏了。

#### Key 命名规范

```typescript
sys.localStorage.setItem(`level_icon_${tableId}`, JSON.stringify(json));
const str = sys.localStorage.getItem(`level_icon_${tableId}`);
const json = str ? JSON.parse(str) : null;
```

**必须加 feature 前缀**（`level_icon_` / `myApp_`），全局 KV 空间是共享的，没前缀迟早撞。

**容量上限**：

| 平台 | 上限 |
|---|---|
| H5（浏览器） | 5~10MB |
| 微信小游戏 | 10MB |
| 原生 | 理论无上限（本地文件） |

**超过上限会抛异常**，大缓存要做 LRU 淘汰或者别用 localStorage（上 IndexedDB / jsb.fileUtils）。

---

### 5.2 prewarmLocalCache — 首屏预热

#### 问题

光有 localStorage 不够。Boot 时没预热的话，第一次滚动还是要走"读盘 → 解码"。

#### 方案

Boot 末尾遍历列表，命中的直接解码入库 + state=2：

```typescript
private prewarmFromLocal(): number {
    let hits = 0;
    for (let i = 0; i < this.data.length; i++) {
        const tableId = this.data[i].tableId;
        const str = sys.localStorage.getItem(`level_icon_${tableId}`);
        if (!str) continue;

        try {
            const raw = JSON.parse(str) as { gridSize: number; palette: string[]; pixels: string };
            const pixels = decodePixels(raw.gridSize, raw.palette, raw.pixels);
            const frame  = createSpriteFrameFromBytes(pixels, raw.gridSize, raw.gridSize);
            LevelIconCache.inst.set(tableId, pixels, frame);
            this.data[i].state = 2;
            hits++;
        } catch {
            sys.localStorage.removeItem(`level_icon_${tableId}`);   // 坏数据清掉
        }
    }
    return hits;
}
```

#### 关键顺序（绝对不能颠倒）

```
setData(data)                 ← ① 拿到完整数据
   ↓
prewarmFromLocal()            ← ② 本地命中的全部预热入库（state 0 → 2）
   ↓
onScroll()                    ← ③ 触发可见区扫描，标 state=1
   ↓
startBatchLoad()              ← ④ 为 state=1 发网络请求
```

**颠倒的后果**：markVisible 在 prewarm 之前 → 已经在本地的 item 也被标成 1 → 白发一次网络请求。

---

### 5.3 preloadTomorrow — 主动投递"明天"

#### 问题

运营每天上新关卡。用户明天开 App 还是要下。

#### 方案

今天进游戏那一刻，悄悄把"明天要上线的 JSON"下到磁盘：

- 只 `setItem`，**不解码**（省 CPU）
- 第二天开 App → prewarm 命中 → 秒出

```typescript
// 登录成功后台任务（低优先级）
function preloadTomorrowIcons(tableIds: number[]) {
    for (const id of tableIds) {
        if (sys.localStorage.getItem(`level_icon_${id}`)) continue;   // 已经有了跳过
        const url = `https://cdn.example.com/levels/${id}.json`;
        assetManager.loadRemote<JsonAsset>(url, (err, json) => {
            if (err || !json) return;
            sys.localStorage.setItem(`level_icon_${id}`, JSON.stringify(json.json));
        });
    }
}
```

#### 和"被动 saveJson"的关系

- **被动缓存**：用户看过的自动落盘
- **preloadTomorrow**：用户还没看过的主动投递
- **两条合体**：用户感受"这游戏每天都秒开"

## 6. CPU 瓶颈（高频事件）

### 6.1 scrolling 节流

#### 问题

`ScrollView` 的 `'scrolling'` 事件 60 FPS 推 = 一秒 60 次。里面如果要算可见区、要标 state、要触发下载，主线程直接被占满。

#### 方案

**节流（throttle）**：规定时间内最多跑一次。

```typescript
private lastScrollT = 0;
private scrollThrottleMs = 16;    // ~60fps，也可以放宽到 33ms（30fps）

private onScroll() {
    const now = Date.now();
    if (now - this.lastScrollT < this.scrollThrottleMs) return;
    this.lastScrollT = now;

    // 可见区计算、标 pending、触发下载 ...
    this.recycleOutOfWindow();
    const newly = this.markVisibleItems();
    if (newly.length > 0) this.startBatchLoad();
}
```

#### 节流 vs 防抖

| 策略 | 适用场景 |
|---|---|
| throttle 节流 | 取样类（scroll 位置、resize） |
| debounce 防抖 | "停下来才处理"（搜索框输入、ScrollView 的 `scroll-ended`） |

**Cocos 3.x 的 `'scroll-ended'` 事件本身就是防抖**：滚动停止一小段时间才触发一次。如果你只在停下来时加载，就直接监听它，连节流都不用写。

#### 什么时候加

**节流是优化，不是洁癖**。先跑起来，发现 scrolling 真的是瓶颈再加。绝大多数场景可见区计算本身便宜，节流反而引入 16ms 延迟。

---

### 6.2 Set 代替数组遍历 — 冗余索引换时间

#### 问题

- 回收时要找所有 state=2 项 → 扫 `data` 全表？O(N)
- startBatchLoad 要找所有 state=1 项 → 扫全表？O(N)

#### 方案

维护 `loadedSet: Set<number>` 和 `pendingSet: Set<number>`（见 3.3 的 `LevelIconCache`）：

- 信息**冗余**（`data[i].state` 里也能扫出来）
- 遍历从 O(N) 降到 O(loaded) / O(pending)
- N=100 差不多，**N=10000 差一个数量级**

**心法**：**"访问模式决定数据结构"**。如果你知道"只关心某个子集"，就**维护那个子集的索引**，别指望 `filter` 扫全表。

---

### 6.3 避免无谓重绘

#### 问题

`setString` / `setSpriteFrame` 即使新旧值相同，Cocos 3.x 仍然会触发 dirty flag 走一遍更新。每次 `onScroll` 无脑重新赋值 label.string = 'Lv ' + data.name = 60 次/秒全量刷字 = 卡。

#### 方案

**有变化才赋值**：

```typescript
private renderRow(rowNode: Node, rowIndex: number) {
    for (let c = 0; c < this.cols; c++) {
        const idx = rowIndex * this.cols + c;
        if (idx >= this.data.length) { ... continue; }

        const cell = rowNode.children[c];
        const label = cell.getChildByName('name')!.getComponent(Label)!;
        const sprite = cell.getChildByName('icon')!.getComponent(Sprite)!;

        const newName = this.data[idx].name;
        if (label.string !== newName) label.string = newName;   // ⭐ 差才改

        const newFrame = LevelIconCache.inst.getFrame(this.data[idx].tableId) ?? this.defaultFrame;
        if (sprite.spriteFrame !== newFrame) sprite.spriteFrame = newFrame;
    }
}
```

## 7. 事件分发瓶颈

### 7.1 事件源判断 — 不是给我的事件早返回

#### 问题

列表 item 的点击事件往往会被父节点冒泡接到，然后父节点里要判"这次点击是不是在关卡区内"。如果全局 Pointer 也监听了，一次点击会唤多个 handler。

#### 方案

冒泡阶段里**尽早判断事件源**，不是给我的事件立刻 return：

```typescript
onItemClicked(event: EventTouch) {
    // event.target 是触发节点，event.currentTarget 是当前接收节点
    const target = event.target;
    if (!target.name.startsWith('LevelItem_')) return;   // 不是关卡 item 直接走人

    const tableId = Number(target.name.substring('LevelItem_'.length));
    this.enterLevel(tableId);
    event.propagationStopped = true;                     // 阻止继续冒泡
}
```

#### 更省事的做法：按节点绑，不按全局绑

Cocos 3.x 的事件系统天然支持"绑在哪个节点就只有经过这个节点的事件触发"：

```typescript
// ✅ 只监听 content 节点下的 touch-end
this.content.on(Node.EventType.TOUCH_END, this.onItemClicked, this);

// ❌ 绑到 canvas / 场景根上，所有触摸都要过这个函数
director.getScene().on(Node.EventType.TOUCH_END, ...);
```

**"事件只在该到达的地方接收"** 就是事件层面的 `routeCondition`。

---

### 7.2 `EventTarget` 总线 vs `import` 直调

#### 真相矩阵

| 做法 | 耦合度 | 适用场景 |
|---|---|---|
| `levelModule.import(listModule).refresh()` | 强耦合：编译期依赖 | 同模块内、明确的父子关系 |
| `GlobalEvent.emit('LevelCompleted', {id})` | 松耦合：运行时名字约定 | 跨模块、跨场景通信 |

#### 常见错

**关卡模块**里直接 `import LevelListController` 然后调 `.refresh()` —— 以后关卡模块想独立打包（分包）就做不到，因为它硬依赖了列表模块。

#### 正确做法

```typescript
// 一个全局事件总线（简单场景直接用 EventTarget，复杂的上 mitt/tapable）
import { EventTarget } from 'cc';
export const GameEvent = new EventTarget();

// 关卡模块
GameEvent.emit('level-completed', { tableId: 101, stars: 3 });

// 列表模块（不 import 关卡代码）
onLoad() {
    GameEvent.on('level-completed', this.onLevelCompleted, this);
}
onDestroy() {
    GameEvent.off('level-completed', this.onLevelCompleted, this);
}
```

**模块间解耦不是"不通信"，是"通过事件名通信、不互相 import 对方的类互相调用"**。

## 8. 生产稳定性

### 8.1 失败自愈 — state 图闭合

**原则**：链上每一步失败都能**退回合法状态**：

| 失败点 | 处理 | 结果 |
|---|---|---|
| `assetManager.loadRemote` 失败 | `data[idx].state = 0` | 重滚回来自然重试 |
| `sys.localStorage.setItem` 抛异常（超容量） | try/catch 吞错误 | 下次 getItem null → 走网络 |
| `JSON.parse` 抛异常（脏数据） | catch + `removeItem` | 下次视为没缓存，走网络 |
| 分页 `_N.json` 404 | 视为终点 | 停止探页 |
| idx 快路径不命中（分页追加移位） | 按 tableId `findIndex` | 定位到真实位置继续 |

**整条链上没有 panic**。任何意外 = 退回合法状态。

---

### 8.2 tableId 快路径 + fallback

#### 问题

发请求时记录 `entry.idx=5`，下载完成时分页追加已经把这个 item 挤到 idx=27。直接用 entry.idx 回写 state → 写到别人身上。

#### 方案

```typescript
let idx = entry.idx;
if (this.data[idx]?.tableId !== entry.tableId) {
    idx = this.data.findIndex(d => d.tableId === entry.tableId);
    if (idx < 0) return;   // 条目已被移除
}
```

**数据结构冗余**（entry 同时存 idx 和 tableId）换**对"列表变化"的健壮性**。

---

### 8.3 失败上报去重 — failReportedIds

#### 问题

一个 URL 坏了 → 回收后滚回来 → 再下 → 再失败 → 再上报 → 死循环里后台埋点被刷爆。

#### 方案

一个 `Set<number>` 记"这个 tableId 本次会话已上报过失败"：

```typescript
private failReportedIds = new Set<number>();

private traceDownloadFail(tableId: number, msg?: string) {
    if (this.failReportedIds.has(tableId)) return;   // 同会话同 id 只报一次
    this.failReportedIds.add(tableId);
    Analytics.trace('AssetDownloadFail', { tableId, msg });
}
```

**客户端小集合** 换 **后台免雪崩**。

---

### 8.4 埋点全家桶 — 下载链路可观测

一个生产级列表至少埋这几个点：

| 埋点 | 时机 | 记录 |
|---|---|---|
| `AssetDownloadStart` | `loadRemote` 调用前 | tableId |
| `AssetDownloadSuccess` | 下载成功、解码前 | tableId, durationMs |
| `AssetDownloadFail` | 下载失败 | tableId, errorMsg |
| `ListView` | 进入列表页 | entry source（从哪进来的） |
| `ListItemClick` | 点击 item | tableId, success/fail |

没埋点的业务 = 线上出问题只能看日志猜。**生产项目没商量必上**。

`durationMs` 从 `pendingMap` entry 的 `startTime` 算：`Date.now() - entry.startTime`。

## 9. 架构级优化（让前面所有优化都省力）

### 9.1 三态机 `state: 0 / 1 / 2`

见 4.1。

**为什么值钱**：用一个 `number` 把"从未下过 / 正在下 / 已下载 / 回收过"四种状态用三个数字表达完，没有 if/else 大爆炸。**这是数据结构消除特殊情况的典范**。

---

### 9.2 lastPlayedIndex — 一个数字一个优化

见 2.3。

**哲学**：**"好的优化不是增加代码，是增加一个数字让别人少写代码"**。

---

### 9.3 冗余索引 loadedSet / pendingSet

见 3.2 / 6.2。

**核心观点**：**信息冗余 = 拿空间换时间**。知道下一步只想遍历子集 → 立刻建子集索引，不要指望 `filter` 扫全表。

---

### 9.4 事件驱动 ≠ `import` 调用

见 7.2。

- **坏**：A 模块 `import B`，调用 `b.doSomething()`
- **好**：A 模块 `emit`，B 模块 `on`

#### 为什么

- `import` 调用 = 编译期强耦合，A 改接口 B 全崩，分包打不开
- 事件驱动 = 运行时松耦合，只要事件名 + payload 语义不变，双方可独立演进

## 11. 从零开始的 13 步落地顺序

按**依赖关系**推进，每一步都是下一步的前置。**每步单独部署 + 自检，别跳步**。

```
1.  LevelData interface + 列表数据源         ← 数据骨架（tableId、name、state）
2.  VirtualList 组件 + ScrollView Prefab     ← 虚拟列表空壳（2.1）
3.  setData 挂真实数据                       ← 首屏静态展示
4.  scrolling → markVisibleItems             ← 滚动触发可见区扫描（4.1）
5.  startBatchLoad                           ← state=1 发 loadRemote（4.2）
6.  onJsonLoaded + decode                    ← 回调入库（4.2 + 2.2）
7.  Texture2D 构造 + SpriteFrame 显示        ← 真图（2.2 + 3.1）
8.  recycleOutOfWindow                       ← 窗外回收（3.2）
9.  sys.localStorage + prewarmFromLocal      ← 本地缓存 + 二次启动（5.1 + 5.2）
10. 点击 item 进关卡 + lastPlayedIndex       ← 进二级页面
11. onReturnFromLevel + renderRow            ← 回家精修（2.3）
12. Pagination                               ← 分页（4.3，生产加）
13. preloadTomorrow + Trace + Throttle       ← 预加载 + 埋点 + 节流（5.3 + 8.4 + 6.1）
```

## 12. 常见踩坑清单

| 症状 | 可能原因 | 对应章节 |
|---|---|---|
| 滚动时已加载的 item 变灰、松手又恢复 | 保留窗 < 可见区，正在可见的被回收 | 3.2 |
| 首屏只显示部分 item，滚动后不下载 | `scrolling` 事件没绑 或 `setContentSize` 没调 | 2.1 + 4.1 |
| 回调找不到 entry，UI 卡 state=1 | `pendingMap` 用单值而非数组 | 4.2 |
| 二次启动仍然全走网络 | prewarm 调在 markVisible 之后 | 5.2 |
| 分页追加后 item 显示但不滚 | append 后没重设 `content.setContentSize` | 4.3 |
| 真机内存持续涨不回收 | SpriteFrame 没 `decRef/destroy` | 3.1 |
| FPS 卡在滚动上 | scrolling 里每帧跑重活，没节流 | 6.1 |
| Draw Call 飙到几百 | 没开动态图集或 icon 尺寸超限 | 2.2 |
| 点击没反应 | Prefab 里 item 根节点没挂 `UITransform` 或没调 `setContentSize` | 2.1 + 7.1 |

## 13. 结语

**N 关卡选择界面**这个题目，本质是"**如何在有限资源下处理大量同构数据**" —— 这个问题的解法**不专属于游戏**，也不专属于 Cocos：

- 做网页列表：虚拟滚动 + 按需加载 + IndexedDB 缓存 = 同一套思路，技术栈不同
- 做 Feed 流：分页 + 预加载 + 精修刷新 = 同一套思路
- 做即时通讯：消息虚拟列表 + 本地存储 + 失败自愈 = 同一套思路
- 甚至做商城、做装备列表、做成就页 = 全都是这一套

**你学的不是"关卡列表怎么写"，是"大量同构数据 UI 的通用思路"**。

---

### 五条记忆锚点

1. **数据结构先于算法** —— `loadedSet` / `pendingMap` / `lastPlayedIndex`，每个优化本质都是换个数据结构
2. **消除特殊情况** —— 三态机让"回收/未下/在下"用同一套逻辑，没有 if 大爆炸
3. **失败 = 退回合法状态** —— 任何错误都能回到 state=0
4. **事件驱动不是 import** —— 模块间永远通过事件名通信
5. **优化是响应瓶颈，不是洁癖** —— 先跑起来测数据，再决定加哪条

### 附：本文涉及的所有 Cocos 3.x API 速查

**UI / 渲染**

- `ScrollView` —— `getScrollOffset() / 'scrolling' / 'scroll-ended'`
- `UITransform.setContentSize(w, h)` —— 设置节点尺寸
- `instantiate(prefab)` —— 克隆节点
- `Sprite.spriteFrame` / `Label.string` —— 显示属性
- `Texture2D / ImageAsset / SpriteFrame` —— 贴图三件套
- `tex.setFilters(NEAREST, NEAREST)` —— 像素图必须

**资源 / 网络**

- `resources.load(path, type, cb)` —— 包内资源
- `assetManager.loadRemote(url, cb)` —— 远端资源
- `assetManager.loadBundle(name, cb)` —— 分包
- `sys.localStorage.setItem / getItem / removeItem` —— 跨平台 KV
- `asset.addRef() / decRef() / destroy()` —— 资源引用管理

**事件**

- `node.on(type, cb, this, useCapture?)` —— 节点事件
- `EventTarget` —— 自定义事件总线
- `event.propagationStopped = true` —— 阻止冒泡
- `Node.EventType.TOUCH_END / TOUCH_START` —— 触摸

**工具**

- `computeVisibleRange(offset, viewport, itemSize, total, buffer)` —— 自己写的工具函数
- `decodePixels(gridSize, palette, rle)` —— RLE 解码

记不住的时候回头翻对应章节，用到一个记一个。**工具不重要，用它解决什么问题才重要**。
